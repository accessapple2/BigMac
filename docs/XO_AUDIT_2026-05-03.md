### #2 — Identify and fix the trader-service restart loop
**Severity:** Critical
**Effort:** 4 hours (investigation-heavy)
**Impact:** Eliminates a quiet operational-availability hazard. Restart-during-market-open is the worst-case timing.
**Why it matters:** `launchctl print gui/501/com.trademinds.trader` reports `runs = 23`, `forks = 31`, `immediate reason = inefficient`. `trader.log` contains 6 `[Errno 48] address already in use` bind failures. The service is `keepalive | runatload`, so after a crash launchd retries within 10 s (`minimum runtime`), and if uvicorn hasn't released port 8080 it crashes again. Today's `[19:58:27]` lifecycle entries in `trader.log` show the service running normally now — but the run-count says it has been bouncy.
**Evidence:**
- `launchctl print gui/$(id -u)/com.trademinds.trader | grep -E "runs|forks|reason"` → `runs=23 / forks=31 / reason=inefficient`
- `grep -n "bind on address" logs/trader.log` → 6 hits, line 1610 / 2219 / 237565 / 237829 / 238116 / 238384
- `pid=87779`, started 15:45 MST (B15 fix deploy)
**Proposed approach:** (a) Add a `pre-launchctl` `lsof -i:8080` check that aborts the service start if the port is occupied. (b) Increase `exit timeout` from 5 s to 30 s in the plist so uvicorn flushes WAL and releases the port. (c) Capture the trigger by adding a `kill -SIGTERM` handler in `main.py` that writes the cause + uptime + last-completed scheduler job to `logs/trader_lifecycle.log`. (d) Read `forks=31` (more than `runs=23`) — that delta typically means the watchdog is forking sub-processes; check `engine/ollama_watchdog.py` for a leak.
**Risk if delayed:** A crash during 06:30 ET market-open with a 5-s exit timeout could leave uvicorn holding port 8080 and trigger a self-DoS.

### #5 — Build & document a backup restore protocol; extend retention
**Severity:** High
**Effort:** 3 hours
**Impact:** Turns "we have backups" from theoretical into proven recovery. Doubles retention horizon for slow-burn corruption detection.
**Why it matters:** Daily SQLite copies exist at `backups/trader_2026-MM-DD.db` (7 dailies, 2026-04-27 → 2026-05-03, ~200 MB each). They're produced by `healthcheck.py:415 backup_trader_db()`. There is **no documented restore command, no integrity check after copy, and no test of the restore path on the live system**. The Sacred Data Rules forbid `rm` of `trader.db` but say nothing about restore drills. SQLite hot-backup via `cp` while WAL is open can produce a torn copy without `sqlite3 .backup` semantics — should be verified.
**Evidence:**
- `healthcheck.py:415` `backup_trader_db()` performs a plain `shutil.copy2` of `trader.db` (and `-shm`, `-wal`)
- `ls backups/trader_*.db | wc -l` → 7
- No `.md` file under `docs/` documents restore steps; no `scripts/restore_trader_db.py`
**Proposed approach:** (a) Replace the `cp` in `backup_trader_db()` with the SQLite Online Backup API (`sqlite3 src.db ".backup dst.db"` or `python sqlite3.Connection.backup`). (b) Add a post-copy integrity check: `PRAGMA integrity_check` against the copy; alert via NTFY if it fails. (c) Write `docs/RESTORE_PROTOCOL.md` covering the three scenarios: corrupt live DB, accidental schema change, and recovery to a specific timestamp. (d) Once a quarter, restore yesterday's backup into `/tmp/trader_restore_test.db` and run `SELECT COUNT(*) FROM trades` against it to prove the bytes are usable. (e) Extend retention to 30 days (cost: ~6 GB at current 200 MB/day; cheap on 16 GB-RAM Mac with whatever disk).
**Risk if delayed:** A corrupt-but-running DB (e.g. an `sma_signals` index drift) is rolled forward to all 7 backups before anyone notices. Then there's no clean checkpoint to recover to.
