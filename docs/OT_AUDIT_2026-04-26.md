## Executive Summary

- **Port 9000 is healthy** but `/api/signals/all` still takes **5.2 seconds** — the caching fix from April helped (was 35s) but the endpoint is not fast yet; signals.db is 601MB and growing.
- **index.html is a code emergency**: 1.8MB, 33,940 lines in a single file. This is the single biggest development risk in the codebase — every future sprint that touches the dashboard adds to a file that already defeats syntax highlighters, grep, and any sane diff review.
- **app.py has 30 duplicate route registrations** (FastAPI silently kills the second copy). Several core areas are affected: backtest, options chain, market data, screener, rikers-log.
- **~40 engine tools are orphaned** — not imported anywhere in main.py or app.py. Includes 5 superseded super_backtest versions, a dead fast_scanner, and multiple strategy experiments that never graduated.
- **Navigation has 10 ghost sections** reachable only by programmatic call (troi, xo-room, rikers-log, economy, etc.) and 3 standalone HTML pages with no sidebar entry.

## F. Top 5 High-Level Recommendations

---

### F1. Break index.html Into Section Modules

**Problem (concrete data):** `dashboard/static/index.html` is **1,897,254 bytes (1.8MB)** and **33,940 lines** — 6.8× over any sane single-file limit. It contains 99 section IDs, thousands of lines of inline JavaScript, and the full CSS for the entire dashboard. Every sprint that adds a feature appends to this file. It already defeats `grep`, Git diffs are unreadable, syntax highlighters crash, and the file takes several seconds to load cold in a browser.

**Proposed change:** Adopt a section-module loading pattern. Each major section (ready-room, leaderboard, ollie, metals, etc.) becomes a separate `/static/sections/section-name.html` file loaded via `fetch()` on first navigation. The shell index.html drops from 1.8MB to ~100KB containing only the sidebar, layout skeleton, shared CSS/JS utilities, and a lazy-loader.

**Effort:** Large (1-2 drydock sessions)
**Risk:** Medium — the fetch-on-demand pattern is well-established; risk is in migrating inter-section JS dependencies
**Why now:** Every future sprint increases the blast radius. The 33,940-line file already has 30 duplicate routes in app.py — that's a symptom of a codebase where finding things has become hard enough that people add new endpoints instead of finding existing ones.

---

### F2. Kill the 30 Duplicate Routes in app.py

**Problem (concrete data):** Grep identified **30 duplicate route paths** in `dashboard/app.py`. In FastAPI, when two `@app.get("/same/path")` decorators exist, the **first registration wins** — the second is silently unreachable. Confirmed duplicates include:

- `/api/backtest/history` (3 registrations found)

### F4. Archive signals.db Before It Hits 1GB

**Effort:** Medium (query changes + archival script)
**Risk:** Low — archival is additive; signals.db stays intact; archive DB is queryable if needed
**Why now:** The 5.2s endpoint will regress to 10s+ as the DB grows. The fix is cheap now; it's expensive after a crash.
