ITEM 2 — Ollama cancel-on-timeout fix
════════════════════════════════════════════════════════════════════════════════
Root cause (full detail in project_hm_wr_ollama_queue_starvation.md):
HM-WR-VRAM-THRASHING shipped a 90s per-provider timeout at the WR-cycle loop
level. When exceeded, the loop emits [WR-PROVIDER-TIMEOUT] and moves on —
BUT the underlying requests.post(... ollama) HTTP call is NOT cancelled. The
inference keeps running on the Ollama server, completes whenever VRAM/queue
permits, and gets discarded (WR loop already moved past). Compute is wasted
AND the queue stays loaded with abandoned work.

Two agents are currently halt_mode='exit_only' as mitigation (set 2026-05-21
14:51:46 UTC): dalio-metals + ollama-kimi. Both reactivate after this fix
ships and one full WR cycle proves no [WR-PROVIDER-TIMEOUT] on ministral-3:3b.

Implementation steps:
  1. Find the Ollama HTTP wrapper. Likely candidates:
       grep -rn "ollama.*generate\|/api/generate\|requests.post.*11434" \
         engine/ providers/ 2>/dev/null | head -10
     The wrapper probably lives at engine/providers/ollama.py or
     engine/ollama_client.py.

  2. Identify the WR-loop timeout site:
       grep -rn "WR-PROVIDER-TIMEOUT\|provider_timeout\|provider.*90" \
         engine/ | head -10

  3. Inspect both. The cancellation needs to be wired such that when the
     WR-loop timeout trips, the in-flight request gets closed:
       - If using requests.Session: call session.close() on timeout
       - If using bare requests.post(timeout=X): the timeout already aborts
         locally; the SERVER may keep running but we stop waiting (lower-
         severity fix — confirm Alpaca/Ollama behavior)
       - Best: switch to a requests.Session held in a contextmanager so the
         WR-loop wrapper can force-close it when its outer timeout trips

  4. Minimum viable fix per the memo:
       Option (a, simplest): ensure each Ollama call uses a fresh Session
       and the WR-loop wrapper closes it on outer timeout. Adds ~10-20 LOC.
       Option (b, robust): module-level _in_flight dict keyed by model_id;
       second arrival for same model either reuses first's result or is
       rejected with [WR-PROVIDER-IN-FLIGHT]. Adds ~30-50 LOC.

  5. Write a test that fails today and passes after the fix:
       - Mock a slow Ollama response (sleep 120s before returning)
       - Call the wrapper with a 90s outer timeout
       - After 90s, verify the wrapper returned/raised AND the underlying
         HTTP connection was closed (use a spy on requests.Session.close
         or check via httpretty/responses library)

  6. py_compile every modified .py:
       venv/bin/python3 -m py_compile engine/providers/ollama.py    # or actual path

  7. Branch + ship:
       git checkout -b hm-wr-cancel-on-timeout
       git add <paths>
       git commit -m "<descriptive HM-WR-CANCEL-ON-TIMEOUT message>"
       git push -u origin hm-wr-cancel-on-timeout

ITEM 3 — get_bulk_prices fixture bug fix
════════════════════════════════════════════════════════════════════════════════
Root cause (full detail in project_hm_bulk_prices_fixture_bug.md):
engine.market_data::get_bulk_prices returns change_pct=0.0 + volume=40 for
all 508 symbols on Alpaca's bulk quotes endpoint. Affects two consumer
surfaces:
  - /api/market/heatmap (Sectors Watchlist heatmap shows all zeros)
  - /api/market-movers (Starfleet was repointed by HM-STARFLEET-MOVERS-FIX
    earlier today; this endpoint still bleeds fixture data)

Strong hypothesis: HM-AQ-β v3 2026-05-07 migration switched from
get_stock_price per-symbol fanout to a single bulk call against
/v2/stocks/quotes/latest. That endpoint returns QUOTES (bid/ask), NOT
TRADES — there's no volume in the quote payload, so the parser probably
fills volume=40 as a default. change_pct=0 likely because the parser
computes against bid/ask midpoint instead of prev_close vs last_trade.

Implementation steps:
  1. Read engine/market_data.py:
       grep -n "def get_bulk_prices\|def get_stock_price\|stocks/quotes\|stocks/bars" \
         engine/market_data.py
     Find both get_bulk_prices and the working get_stock_price for diff.

  2. Inspect the Alpaca endpoint URL used in get_bulk_prices. If it's
     /v2/stocks/quotes/latest, the bug is structural: quotes don't have
     volume. Two fix paths:

       a. Switch to /v2/stocks/bars/latest (returns OHLCV including volume
          and prev_close → change_pct can be computed against open or
          prev_close). Cleanest.

       b. Keep /v2/stocks/quotes/latest for prices but also call
          /v2/stocks/bars/latest in parallel for volume/change_pct.
          Combine. More HTTP calls but stays compatible.

       Option (a) is recommended unless there's a documented reason for
       quotes (e.g., need bid/ask spread).

     non-zero change_pct reflecting today's move.

       venv/bin/python3 -m py_compile engine/market_data.py
